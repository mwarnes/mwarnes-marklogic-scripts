# Security must-gather (`ml-security-gather.py`)

One read-only script that collects what MarkLogic Support needs for a security problem and checks it for the usual
mistakes. The first argument is the security area; the other options belong to that area.

```
ml-security-gather.py AREA [options]       AREA = saml | oauth | ldap | https
ml-security-gather.py AREA --help          options and examples for one area
```

| Area | Reads | Optional extras |
|---|---|---|
| `saml` | SAML profile, stored IdP/SP certificates, bound app servers, user/role external names | `--idp-metadata`, `--saml-response`, `--user-name`, `--logs` |
| `oauth` | OAuth profile (Resource server; Authorization code on MarkLogic 12), IdP discovery document, JWKS, IdP TLS chain and whether MarkLogic trusts it | `--token` (signature, issuer, claims, role mapping), `--user-name`, `--logs`, `--no-probe` |
| `ldap` | LDAP profile, its certificates, the directory server's TLS (LDAPS or StartTLS) and whether MarkLogic trusts it | `--user-name`, `--logs`, `--no-probe` |
| `https` | App server TLS settings (MarkLogic 11 and 12 spell them differently), the certificate template and whether its certificate is **TEMPORARY** (generated by MarkLogic, self-signed) or **PERMANENT** (signed by a CA), whether the port serves that certificate, the chain the port really serves, host name, protocols, and certificates in the Security database that share a subject | `--appserver`, `--group`, `--server-ca`, `--probe-host`, `--logs`, `--no-probe` |

Only `--host` and `--user` are required, and the script is meant to be run as the MarkLogic `admin` user. Anything left out
is skipped and listed in the **Not collected** table of `SUMMARY.md` with the option that adds it. The password comes from
`MARKLOGIC_PASS` (or a prompt), never from the command line. Passwords, private keys and client secrets are removed before
anything is written. Output: `./<area>-gather-<timestamp>/` with `SUMMARY.md`, the raw JSON, filtered logs and a `.zip`.

Requirements: `python3` (standard library only), `curl`, `openssl`. Tests: `python3 -m unittest discover -s scripts/Security/tests`.

Companion for the logs: `ml-trace-events.py enable|disable|status --preset saml|oauth|ldap` (in the MarkLogic support skill's
`assets/support-scripts`) switches the trace events on before the test and off afterwards.

## Temporary versus permanent certificates (`https`)

MarkLogic generates a self-signed *temporary* certificate for a template that has `generate-temp-certificate` set. The
Management API says which certificates are temporary: `GET /manage/v2/certificates/<id>` (host certificates) and
`GET /manage/v2/certificate-authorities/<id>` (authorities, including the temporary ones) return `temporary`, `template-id`
and `template-version`. The report lists, per template, each certificate as **TEMPORARY** or **PERMANENT** (and who signed
it), warns when only a temporary certificate exists, compares the serial of the certificate the port serves with the
template's certificates, and notes a certificate issued for an older template version.

## Duplicate subjects

MarkLogic logs `Duplicate certificate subject found in Security Database` (a Warning, in pairs). The report groups every
certificate by its full subject and says what each group is: host certificates held by two templates (for example RSA and
EC), the same key in a self-signed root and its cross-signed copy, old certificates without a key identifier, or **different
keys under one subject** (a warning). It also shows that the names in the certificate-authority list are the **issuer's**
name, not the certificate's own, so an imported intermediate appears under its root's name and the list looks full of
duplicates. What triggers the log line was not found (not reproducible with API reads or TLS handshakes).

## Let's Encrypt import (checked 2026-10-25, MarkLogic 12.1.0)

Certbot (Route 53 DNS-01) plus `marklogic-cert-deploy-wrapper.sh` pushed a Let's Encrypt certificate into a new template; the
`https` area reported it as PERMANENT, issued by Let's Encrypt, served by the port, name matching. Two things to know: a template
created through the Management API holds **no** certificate until one is imported (the app server then fails the TLS handshake and
the ErrorLog says `Failed to find server certificate in certificate template <id>`), and the port sent only the leaf
certificate. **Tested fix:** import the issuing CA certificate (the intermediate, second block of `fullchain.pem`) into MarkLogic's trusted
certificate authorities (`pki:insert-trusted-certificates` in the Security database); the port then sends leaf + intermediate at once.
A bundle in the certificate import itself is rejected (`insert-host-certificates` takes one certificate, HTTP 400 `PKI-BADCERTIFICATE`).

## SAML authorization rule and the user option

On MarkLogic 11.3.7 and 12.1 SAML works only when **both `authentication` and `authorization` are `saml`**, with roles mapped
through role external names (earlier releases accepted `internal`). Tested: with `internal` the login succeeds but the identity
gets no roles (HTTP 403) whether a user's external name, an internal user's name, or both equal the NameID. The `saml` area
reports a profile whose authorization is not `saml` as a failure (a warning before 11.3.7) and warns when no role has an
external name. `--user` is required (it is not defaulted to `admin`); use any MarkLogic user with the admin role, or set
`MARKLOGIC_USER`.
